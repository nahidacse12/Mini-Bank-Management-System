
# Mini Bank Management System API

A Django REST Framework coursework project that provides user registration, JWT authentication, profile management, bank account management, deposits, withdrawals, money transfers, transaction history, filtering, pagination, and admin-only endpoints.

## Features

- User registration and JWT authentication
- View and update the authenticated user's profile
- Create and view personal bank accounts
- Savings and Current account types
- Unique account numbers generated by the server
- Account balance endpoint
- Deposit and withdrawal operations
- Money transfers between bank accounts
- Transaction history with filtering and pagination
- Admin-only customer, account, and transaction lists
- Automated API tests

## Technologies

- Python
- Django
- Django REST Framework
- Simple JWT
- django-filter
- SQLite

## Requirements

- Python 3.10 or later
- pip

## Setup and Installation

### 1. Clone the repository

```bash
git clone YOUR_GITHUB_REPOSITORY_URL
cd mini-bank-management
```

Replace `YOUR_GITHUB_REPOSITORY_URL` with your actual GitHub repository URL.

If you already have the project files on your computer, open the project directory instead.

### 2. Create a virtual environment

```bash
python -m venv venv
```

### 3. Activate the virtual environment

Windows Command Prompt:

```bat
venv\Scripts\activate
```

Windows PowerShell:

```powershell
.\venv\Scripts\Activate.ps1
```

macOS/Linux:

```bash
source venv/bin/activate
```

### 4. Install dependencies

```bash
pip install -r requirements.txt
```

### 5. Apply database migrations

```bash
python manage.py makemigrations banking
python manage.py migrate
```

### 6. Create an administrator

```bash
python manage.py createsuperuser
```

Follow the prompts to create the admin account.

### 7. Run the development server

```bash
python manage.py runserver
```

Base API URL:

http://127.0.0.1:8000/api/

Django admin:

http://127.0.0.1:8000/admin/

## Authentication

Registration and login endpoints are public. Other API endpoints require authentication unless otherwise specified.

### Register a user

**POST** `/api/auth/register/`

Example request:

```json
{
  "username": "alice",
  "email": "alice@example.com",
  "password": "StrongPass123!",
  "first_name": "Alice",
  "last_name": "Example"
}
```

### Obtain JWT tokens

**POST** `/api/auth/login/`

Example request:

```json
{
  "username": "alice",
  "password": "StrongPass123!"
}
```

The response includes an access token and a refresh token.

Use the access token in the Authorization header:

```text
Authorization: Bearer YOUR_ACCESS_TOKEN
```

### Refresh an access token

**POST** `/api/auth/refresh/`

Example request:

```json
{
  "refresh": "YOUR_REFRESH_TOKEN"
}
```

## API Endpoints

All paths below are relative to:

`http://127.0.0.1:8000`

### Authentication

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/auth/register/` | Register a user |
| POST | `/api/auth/login/` | Obtain JWT tokens |
| POST | `/api/auth/refresh/` | Refresh an access token |

### Profile

| Method | Endpoint | Description |
|---|---|---|
| GET | `/api/profile/` | View your profile |
| PATCH | `/api/profile/` | Update editable profile fields |

Users can access their own profile.

### Bank Accounts

| Method | Endpoint | Description |
|---|---|---|

| Method | Endpoint | Description |

| Method | Endpoint | Description |

## Creating a Bank Account

**POST** `/api/accounts/`

Authorization:

```text
Authorization: Bearer YOUR_ACCESS_TOKEN
```

Example request:

```json
{
  "account_type": "savings"
}
```

For a current account, use:

```json
{
  "account_type": "current"
}
```

The server generates the account number and assigns the account to the authenticated user. The client cannot set the initial balance or account status through this serializer.

## Depositing Money

**POST** `/api/transactions/deposit/`

Example request:

```json
{
  "account_id": 1,
  "amount": "100.00",
  "description": "Deposit"
}
```

The account must belong to the authenticated user and be active. The amount must be greater than zero.

## Withdrawing Money

**POST** `/api/transactions/withdraw/`

Example request:

```json
{
  "account_id": 1,
  "amount": "25.00",
  "description": "Withdrawal"
}
```

The account must belong to the authenticated user and be active. Withdrawals exceeding the available balance are rejected.

## Transferring Money

**POST** `/api/transactions/transfer/`

Example request:

```json
{
  "from_account_id": 1,
  "to_account_number": "RECEIVERACCOUNT",
  "amount": "10.00",
  "description": "Transfer"
}
```

Replace the example account ID and account number with valid values.

Both accounts must be active. Transfers to the same account and transfers exceeding the sender's balance are rejected.

A successful transfer creates two transaction records:

- `transfer_sent` for the sender
- `transfer_received` for the receiver

## Transaction History, Filtering, and Pagination

**GET** `/api/transactions/`

Example requests:

```text
/api/transactions/
/api/transactions/?type=deposit
/api/transactions/?type=withdrawal
/api/transactions/?type=transfer_sent
/api/transactions/?page=2
/api/transactions/?type=deposit&page=1
```

The transaction type filter accepts the transaction types defined by the application:

- `deposit`
- `withdrawal`
- `transfer_sent`
- `transfer_received`

The API uses page-number pagination with 10 records per page by default.

Transaction history should only expose records associated with the authenticated user's accounts.

## Error Handling

The API uses standard HTTP status codes, including:

- `200 OK` — successful retrieval or update
- `201 Created` — successful creation or transaction
- `400 Bad Request` — invalid input or insufficient funds
- `401 Unauthorized` — authentication is missing or invalid
- `403 Forbidden` — permission denied
- `404 Not Found` — requested resource is unavailable

Exact responses depend on the endpoint and validation result.

## Running Tests

Run the automated tests with:

```bash
python manage.py test
```

The current automated test suite covers:

- Preventing access to another customer's account
- Successful deposits
- Rejecting withdrawals with insufficient funds
- Updating balances during transfers
- Creating transfer transaction records
- Rejecting zero-value deposits

Additional tests for registration, permissions, filtering, pagination, and incoming transfers can further improve coverage.

## Security Notes

This project is intended for educational purposes and is not suitable for real banking.

Before production deployment:

- Store secret keys in environment variables.
- Set `DEBUG = False`.
- Configure appropriate allowed hosts.
- Use HTTPS and a production-ready database.
- Configure secure logging, rate limiting, and transaction idempotency.
- Review authentication, permissions, and financial transaction handling.
- Test concurrency behavior against the intended production database.

Database locking behavior, including `select_for_update()`, depends on the database backend.
